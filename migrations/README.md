# Миграции

Схема создаётся при старте (`Database.create_all()`) — на чистой базе этого достаточно.
Но `create_all` умеет только создавать недостающие таблицы: он не добавит колонку
в существующую таблицу и не знает, что на живой базе (`data/live.db`, 36 заказов,
117 решений) уже лежат данные.

Поэтому любое изменение схемы — файл `NNNN_описание.sql` в этом каталоге, применяемый
скриптом. Правка таблицы руками в редакторе БД заканчивается тем, что тесты зелёные
на чистой базе, а данные в другой форме.

```bash
# план без изменений
./.venv/Scripts/python.exe -m migrations.apply --db data/live.db --dry-run
# применить недостающие миграции (повторный запуск ничего не делает)
./.venv/Scripts/python.exe -m migrations.apply --db data/live.db
```

Как работает: таблица `schema_version` хранит применённые версии, файлы берутся
по порядку номеров. Оператор, который упадёт на «уже существует / колонка уже есть»
(база создана через `create_all` уже с новой моделью), пропускается — миграция остаётся
применимой и к старой, и к новой базе.

| Файл | Что делает | Зачем |
|---|---|---|
| `0001_runs_and_audit.sql` | таблица `runs`, колонки `analyses.run_id`, `audit_runs.run_id`, индексы по ним и по `audit_runs.created_at` | без прогона не отвечаются вопросы «сколько стоил прогон» и «что изменилось между прогонами» |
| `0002_aging.sql` | `orders.published_at`, `orders.queued_at`, индексы | «висит больше суток» нельзя посчитать без даты публикации: возраст заказа и наш долг в очереди — разные часы |
| `0003_backfill_queue.sql` | заполняет `queued_at` у заказов, которые ждут проверки сейчас, по времени последнего анализа | иначе «сколько висит» не считается для уже накопленной очереди |

Правила:

- миграция аддитивная: старые строки остаются как есть, `run_id = NULL` означает
  «решение до появления прогонов», а не ошибку;
- номер занят навсегда: изменённая миграция — это новая миграция, а не правка старой;
- Alembic не нужен, пока схема SQLite: `schema_version` + файлы решают ту же задачу
  без зависимости. При переходе на PostgreSQL скрипт применяется внутри `BEGIN/COMMIT`.
