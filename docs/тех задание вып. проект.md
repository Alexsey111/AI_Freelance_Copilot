# Техническое задание

## AI Freelance Copilot — MVP ядра системы автоматизации фриланса

**Назначение:** выпускной учебный проект, который после защиты становится базовым модулем полноценной системы автоматизации поиска и обработки фриланс-заказов.

**Главный принцип:** учебный проект должен быть простым для реализации сейчас, но архитектурно не требовать переписывания при подключении реальных фриланс-площадок, Telegram, RAG/профиля кандидата и автоматической отправки откликов.

---

# 1. Цель проекта

Разработать веб-приложение **AI Freelance Copilot**, которое позволяет:

1. создать запись о фриланс-заказе;
2. сохранить её в БД;
3. отобразить заказы в веб-панели;
4. отправить заказ на ИИ-анализ;
5. определить соответствие заказа профилю исполнителя;
6. сформировать структурированный результат и черновик отклика;
7. при недостатке данных установить `needs_review=true`;
8. сохранить весь процесс в журнале аудита;
9. предоставить человеку возможность проверить сомнительный результат.

### Важное ограничение MVP

На этапе учебного проекта **не требуется реальное подключение к фриланс-площадкам и автоматическая отправка откликов**.

Заказ поступает через API вручную.

Однако архитектура должна предусматривать последующее подключение:

```text
FL.ru
Kwork
Freelance.ru
Telegram
RSS
API
Webhooks
Browser automation
        ↓
   Source Adapter
        ↓
   ЕДИНЫЙ DOMAIN
```

# 3. Архитектура

## 3.1. Архитектурный подход

Использовать **модульный монолит**.

Не делать микросервисы.

Не делать:

```text
frontend → service 1 → service 2 → service 3 → service 4
```

Для учебного проекта это избыточно.

Использовать:

```text
                ┌──────────────────┐
                │   Web UI         │
                │   Streamlit      │
                └────────┬─────────┘
                         │
                         ▼
                ┌──────────────────┐
                │     FastAPI      │
                │   REST API       │
                └────────┬─────────┘
                         │
             ┌───────────┼────────────┐
             ▼           ▼            ▼
        ┌─────────┐ ┌──────────┐ ┌──────────┐
        │ Orders  │ │ Analysis │ │  Audit   │
        │ Domain  │ │ Service  │ │ Service  │
        └────┬────┘ └─────┬────┘ └────┬─────┘
             │            │            │
             └────────────┼────────────┘
                          ▼
                    ┌───────────┐
                    │ Repository│
                    │  Layer    │
                    └─────┬─────┘
                          ▼
                    ┌───────────┐
                    │  SQLite   │
                    └───────────┘

                          │
                          ▼
                   ┌────────────┐
                   │ LLM Adapter│
                   └────────────┘
```

Но внутри кода должна быть возможность впоследствии заменить отдельные компоненты.

# 12. JSON Schema результата

Это принципиальный момент проекта.

LLM **не должна возвращать произвольный текст**.

Внутри приложения должна существовать Pydantic-модель:

```python
class AnalysisResult(BaseModel):
    match_score: float | None
    recommendation: Literal[
        "apply",
        "skip",
        "review"
    ]
    reason: str
    matched_skills: list[str]
    missing_skills: list[str]
    draft_reply: str | None
    needs_review: bool
    review_reason: str | None
```

При этом должны быть проверки:

```text
needs_review = true
        ↓
review_reason обязателен
```

и:

```text
needs_review = false
        ↓
review_reason = null
```

---

# 13. Логика ручной проверки

Это одна из центральных функций проекта.

Система **не должна придумывать отсутствующую информацию**.

Например, заказ:

> Нужен разработчик Python. Подробности обсудим лично.

LLM не должна писать:

> Бюджет проекта 50 000 рублей.

Вместо этого:

```json
{
  "match_score": null,
  "recommendation": "review",
  "reason": "Недостаточно данных для надёжной оценки",
  "matched_skills": ["Python"],
  "missing_skills": [],
  "draft_reply": null,
  "needs_review": true,
  "review_reason": "Не указан бюджет и объём работ"
}
```

---

# 14. Когда автоматически ставить `needs_review=true`

Минимальные правила:

### Случай 1

Не хватает критически важных данных.

### Случай 2

LLM не вернула корректный JSON.

### Случай 3

Не удалось определить соответствие профилю.

### Случай 4

Недостаточно информации для генерации безопасного отклика.

### Случай 5

Произошла ошибка LLM.

# 15. Очень важное архитектурное решение

Не надо позволять LLM самостоятельно решать:

```text
"send_message": true
```

На MVP LLM отвечает только:

```text
что система считает
```

А бизнес-логика решает:

```text
что системе разрешено делать
```

То есть:

```text
             LLM
              ↓
        Recommendation
              ↓
       Business Rules
              ↓
      ┌───────┴────────┐
      ↓                ↓
   safe            needs_review
      ↓                ↓
 result             человек
```

Это хороший архитектурный принцип, который потом позволит безопасно добавить автоматические действия.

# 16. Абстракция LLM

Сразу создать интерфейс:

```python
class LLMProvider(Protocol):

    async def analyze_order(
        self,
        order: Order,
        profile: Profile
    ) -> AnalysisResult:
        ...
```

Конкретная реализация:

```text
LLMProvider
    │
    ├── OpenAIProvider
    ├── OllamaProvider
    └── MockProvider
```

На MVP достаточно:

```text
OpenAIProvider
+
MockProvider
```

А локальную модель можно подключить без изменения бизнес-логики.

---

# 17. Почему нужен `MockProvider`

Чтобы тесты не зависели от API и денег.

Например:

```python
mock_llm.analyze_order(...)
```

возвращает заранее известный результат.

Тогда можно проверить:

```text
API
 ↓
Service
 ↓
Repository
 ↓
Audit
```

без реального вызова LLM.

Это значительно повысит качество проекта.

# 18. Абстракция источника заказов

Вот здесь мы специально готовим фундамент будущей автоматизации.

Создать интерфейс:

```python
class OrderSource(Protocol):

    async def fetch_orders(self) -> list[ExternalOrder]:
        ...
```

Пока:

```text
OrderSource
    │
    └── ManualOrderSource
```

В будущем:

```text
OrderSource
    │
    ├── ManualOrderSource
    ├── FlRuSource
    ├── KworkSource
    ├── FreelanceRuSource
    ├── TelegramSource
    └── RSSSource
```

### Ключевой принцип

Все источники приводят свои данные к единой модели:

```text
ExternalOrder
      ↓
Normalizer
      ↓
Order
```

Поэтому бизнес-логика не знает:

> пришёл заказ с FL.ru или из Telegram.

Она видит только:

```python
Order(...)
```

Это **очень важно для будущего проекта**.

# 19. Абстракция действий

Ещё один слой закладываем заранее.

```python
class ActionExecutor(Protocol):

    async def execute(self, action: Action) -> ActionResult:
        ...
```

Пока реальных действий нет.

В будущем:

```text
ActionExecutor
       │
       ├── TelegramNotification
       ├── DraftProposal
       ├── SendProposal
       ├── SaveToCRM
       └── CreateTask
```

Таким образом выпускной проект уже содержит фундамент будущего:

```text
SOURCE → ANALYZE → DECIDE → ACTION
```

# 29. Правила надёжности

Система должна придерживаться следующих принципов:

### 1. LLM не является источником истины

Она предлагает анализ.

### 2. Отсутствующие данные не выдумываются

Например:

```text
budget = null
```

а не:

```text
budget = 50000
```

### 3. Невалидный JSON = ошибка/ручная проверка

Нельзя молча использовать кривой результат.

### 4. Любой AI-запуск записывается в audit

Даже если он закончился ошибкой.

### 5. Каждый AI-результат привязан к версии prompt

Например:

```text
prompt_version = "v1.0"
```

Это потом позволит сравнивать результаты разных промптов.

# 33. Мини-экономика

В отчёте привести пример.

Например:

### До автоматизации

Ручной разбор одного заказа:

```text
прочитать заказ       3 мин
оценить соответствие  3 мин
написать отклик       5 мин
занести информацию    2 мин
--------------------------
итого                 13 мин
```

100 заказов:

```text
1300 минут
≈ 21,7 часа
```

### После

Человек:

```text
быстрый просмотр       1 мин
проверка AI            1 мин
корректировка          1 мин
--------------------------
≈ 3 мин
```

100 заказов:

```text
300 минут
≈ 5 часов
```

Экономия:

```text
≈ 16,7 часа / 100 заказов
```

В реальном проекте эти цифры заменить фактическими замерами MVP.

# 34. Главная метрика проекта

Не просто:

> «LLM отвечает на запрос».

А:

### Сколько времени человек экономит при обработке одного заказа?

Дополнительные метрики:

* доля корректных JSON;
* доля заказов, требующих review;
* среднее время AI-анализа;
* количество ошибок;
* среднее время обработки заказа;
* процент заказов, которые AI рекомендует к отклику.
