# Отчёт по выпускному проекту «AI Freelance Copilot»

Заполнен строго по шаблону урока. Все числа — из реальных прогонов; там, где нужны ваши данные,
стоит **[ВАШЕ]**. Формулировки для портфолио вынесены в п. 15.

---

## 1. Название выбранного проекта

**AI Freelance Copilot — MVP ядра автоматизации фриланса** (контур `ЗАКАЗ → ИИ-АНАЛИЗ → РЕШЕНИЕ → (человек) → АУДИТ`).

## 2. Ценность (для кого и зачем)

**Для кого:** фрилансер-разработчик (одиночка), который сам ищет заказы и сам пишет отклики.

**Зачем:** время уходит не на работу, а на отбор. Фрилансер просматривает ленту, выясняет, подходит ли
заказ, прикидывает бюджет, пишет отклик, отсеивает мусор. При 13 минутах на заказ и потоке в десятки
заказов в неделю это часы, потраченные на сомнительные предложения.

Система берёт на себя первый проход и оставляет человеку только спорные случаи. Что она даёт:

- разбор заказа за секунды (на живом прогоне — от 1,9 до 20,2 с на реальной модели);
- готовый черновик отклика там, где решение уверенное;
- честное «не знаю» вместо выдуманных цифр: нет бюджета — нет оценки, заказ уходит человеку с причиной;
- восстановимую историю решений: по аудиту видно, почему система сказала «откликаться», «пропустить»
  или «на проверку».

Отличие от «обёртки над LLM»: **модель говорит, что она считает, а что системе разрешено делать —
решает бизнес-логика**. Модель физически не может попросить отправить сообщение клиенту: её ответ
проходит проверку схемой и шесть бизнес-правил, а результат, ушедший на проверку человеку, по
построению безопасен — без выдуманной суммы и без готового к отправке текста.

## 3. Три сценария пользователя

**Сценарий 1. «Заказ мне подходит».**
Фрилансер добавляет заказ («Telegram-бот на Python с ИИ-ассистентом», бюджет 30–50 тыс. ₽) и запускает анализ.
Система: соответствие 100 %, рекомендация «откликаться», совпавшие навыки — Python, FastAPI, PostgreSQL,
Docker, LLM, REST API, парсинг; черновик отклика готов; `needs_review=false`.
На живом прогоне (`gpt-4o-mini`): 20,2 с на вызов.
**Результат:** отклик можно отправлять после быстрой вычитки, решение системы обосновано.

**Сценарий 2. «Не хватает данных».**
Заказ «Доработать backend на Python и Docker», где бюджет «обсудим после оценки».
Система: `match_score = null` (не выдумывает сумму), `recommendation = review`, причина —
«не указан бюджет», черновик отклика отсутствует, заказ попадает в очередь ручной проверки.
Фрилансер открывает очередь, видит причину, уточняет бюджет у заказчика и нажимает «Подтвердить» —
решение уходит в аудит.
**Результат:** ни одной выдуманной цифры в отклике; сомнительный случай решает человек.

**Сценарий 3. «Заказ не мой».**
Заказ «Вёрстка лендинга на Tilda», где в профиле нет вёрстки.
Система: соответствие 0 %, рекомендация «пропустить», `needs_review=false` — человека не дёргают.
**Результат:** очередь ручной проверки остаётся очередью спорных случаев, а не свалкой всего
неподходящего; фрилансер не отвлекается на заведомо чужие заказы.

## 5. Схема данных (таблицы)

SQLite, четыре таблицы, создаются автоматически при старте.

| Таблица | Что хранит | Ключевые поля |
|---|---|---|
| `orders` | заказы | `source`, `external_id` (дедупликация), `title`, `description`, `budget_min/max`, `currency`, `status`, `needs_review`, `created_at`, `updated_at` |
| `analyses` | результаты ИИ-анализа (на заказ — сколько угодно запусков) | `order_id`, `profile_id`, `model_name`, `prompt_version`, `match_score`, `recommendation`, `reason`, `matched_skills`, `missing_skills`, `draft_reply`, `needs_review`, `review_reason`, `raw_response`, `duration_ms`, `review_decision`, `review_comment`, `reviewed_at` |
| `audit_runs` | журнал каждого действия | `action`, `order_id`, `analysis_id`, `status`, `input_payload`, `output_payload`, `error`, `duration_ms`, `created_at` |
| `profiles` | профиль исполнителя | `name`, `skills`, `normalized_skills`, `hourly_rate_rub`, `is_default` |

Связи: `profiles ||--o{ analyses`, `orders ||--o{ analyses`, `orders ||--o{ audit_runs`, `analyses ||--o{ audit_runs`.

Жизненный цикл заказа:

```text
NEW → ANALYZING → ┬→ ANALYZED → APPROVED
                  ├→ NEEDS_REVIEW → ┬→ APPROVED
                  │                 └→ REJECTED
                  └→ ERROR
```

База: `data/app.db` (локально) или volume `copilot-data` в Docker. Посмотреть данные —
`GET /api/v1/orders` и `GET /api/v1/audit`, либо экраны панели «Заказы» и «Аудит и ошибки».

## 6. ИИ-операция

**Что делает модель:** по описанию заказа и профилю исполнителя возвращает оценку соответствия,
рекомендацию, совпавшие/недостающие навыки, объяснение и черновик отклика.

**Провайдер:** OpenAI-совместимый endpoint (в живом прогоне — `gpt-4o-mini` через proxyapi.ru);
по умолчанию `mock` — детерминированный офлайн-провайдер для тестов и демонстраций.

### Схема JSON

Ответ модели — не свободный текст, а строгий контракт (`AnalysisResult`, Pydantic):

```json
{
  "match_score": 0.86,
  "recommendation": "apply",
  "reason": "Заказ полностью соответствует навыкам исполнителя",
  "matched_skills": ["Python", "FastAPI", "Docker"],
  "missing_skills": [],
  "draft_reply": "Здравствуйте! Готов обсудить проект...",
  "needs_review": false,
  "review_reason": null
}
```

Три валидатора делают схему рабочей, а не декоративной:

1. `needs_review=true` требует непустой `review_reason`; `false` требует `review_reason=null`.
2. `needs_review=true` требует `recommendation="review"` и `draft_reply=null` — результат,
   ушедший человеку, безопасен по построению.
3. `extra="forbid"` — модель не может протащить лишнее поле вроде `send_message`.

Невалидный JSON не «разбирается как получится»: он превращается в `LLMInvalidResponseError`,
то есть в ручную проверку.

### Температура

`LLM_TEMPERATURE=0.0`. Анализ заказа — задача классификации с воспроизводимым результатом, а не
творчество: при одной и той же паре «заказ + профиль» система должна выдавать один и тот же вердикт,
иначе решения в аудите невозможно сравнивать между собой. Черновик отклика тоже пишется при нулевой
температуре — он должен звучать как один и тот же исполнитель, а не как разные люди.

### Когда нужна ручная проверка

Шесть правил поверх мнения модели (по ТЗ §14); любое сомнение ведёт к `needs_review=true`:

| Правило | Условие | Причина для человека |
|---|---|---|
| 1. Нехватка критичных данных | нет бюджета или описание короче 40 символов | «не указан бюджет», «описание слишком короткое» |
| 2. Невалидный ответ модели | пришёл не JSON или неполная схема | «Модель вернула невалидный JSON» |
| 3. Низкая уверенность | `match_score` ниже порога 0.35 или модель сама просит проверку | «Низкая уверенность модели (0.10 < 0.35)» |
| 4. `apply` без черновика | рекомендация откликаться, а текста нет или он короче 80 символов | «Недостаточно информации для безопасной генерации отклика» |
| 5. Ошибка LLM | недоступна, таймаут, отказ провайдера | статус заказа `error`, текст ошибки в аудите |
| 6. Расхождение оценок | оценка модели расходится с независимым расчётом по профилю больше чем на 0.5 | «Оценка модели расходится с расчётом по профилю (0.99 против 0.00)» |

Отдельно работает **правило уверенного отказа**: если и модель, и расчёт по профилю дают низкое
соответствие, заказ уходит в `skip`, а не в очередь проверки. Иначе очередь забивается заведомо
чужими заказами и человек перестаёт её смотреть.

## 7. Память / контекст (что хранится и как используется)

**Профиль исполнителя** (`profiles`) — единственный постоянный контекст, который попадает в анализ:
имя, описание, навыки и их нормализованный вид, ставка. Он используется дважды:

1. подставляется в промпт как «кто я», чтобы модель оценивала заказ относительно конкретного
   исполнителя, а не абстрактно;
2. участвует в независимом детерминированном расчёте соответствия (matching engine) — он не
   доверяет самооценке модели и служит второй точкой зрения для правила 6.

**История заказов и анализов** (`orders`, `analyses`) — накапливается и используется на чтение:
витрина, фильтры, очередь проверки, повторные запуски анализа по одному заказу (видно, как меняется
вердикт при изменении профиля или промпта).

**Журнал аудита** (`audit_runs`) — вход и выход каждого действия: по записи восстанавливается,
с каким профилем, какой моделью и какой версией промпта получен результат.

**Версия промпта** (`PROMPT_VERSION = "v1.0"`) сохраняется в каждом анализе — результаты, полученные
на разных версиях промпта, можно сравнивать между собой, а не гадать, почему вердикт изменился.

Векторной памяти и RAG в MVP нет сознательно (ТЗ §22): выбор реальных проектов из портфолио при
генерации отклика — следующий этап, интерфейс под него уже заложен.

## 8. Контроль качества: что валидируется на входе и на выходе

**На входе (точка 1):**

- обязательные поля и типы — Pydantic-схема `OrderCreate` (`extra="forbid"`, лишние поля отвергаются);
- источник заказа — только из перечисления `OrderSource`, иначе HTTP 422 со списком допустимых;
- бюджет: `budget_min <= budget_max`, отрицательные значения отвергаются.
  Если бюджета нет — `null`, а не 0: ноль был бы «нулевым бюджетом» и молча искажал бы решение.

**На выходе (точки 2 и 3):**

- результат анализа — строгая схема `AnalysisResult` с тремя валидаторами (см. п. 6);
- ответ модели, не прошедший схему, не попадает в бизнес-логику: превращается в `LLMInvalidResponseError`
  → `needs_review=true` + причина + запись в аудит;
- фильтры витрины валидируются: неизвестный статус или рекомендация → HTTP 422, а не тихо пустой список;
- пагинация ограничена (`page >= 1`, `page_size` от 1 до 200).

**Тесты и гейты** (фактический прогон):

```text
./.venv/Scripts/python.exe -m pytest              → 121 passed
./.venv/Scripts/python.exe -m pytest --cov=app    → покрытие app/ 96%
./.venv/Scripts/python.exe -m ruff check .        → All checks passed!
./.venv/Scripts/python.exe scripts/check_secrets.py → в репозиторий секреты не уезжают
```

**Набор тестовых данных** `tests_data/` — 15 сценариев, 8 из них приводят к ручной проверке
(по одному на каждое правило из п. 6), 10 запросов витрины с ожидаемыми ответами. Прогоняется двумя
путями: через pytest (31 тест) и сквозным скриптом по живому API с экспортом JSON/CSV.

**Аудит как контроль:** в `audit_runs` попадает каждое ключевое действие, включая неудачные —
`create_order`, `analyze_order`, `review_decision`. На живом прогоне: 3 создания, 3 анализа,
1 решение человека, 2 обращения к витрине, ошибок LLM — 0.

**Найденные и исправленные дефекты** (журнал — `docs/PROJECT_JOURNAL.md`): распад in-memory SQLite
между сессиями; потеря записи аудита при `HTTPException` (хотя ТЗ требует обратного); конфликт имён
`OrderSource`; порядок бизнес-правил (сверка оценки перехватывала правило низкой уверенности);
`localhost` → IPv6-конфликт с ретранслятором Docker; карточка заказа отдавала `latest_analysis=null`
(найдено на живом прогоне, закрыто 4 тестами).

## 10. Мини-экономика

**Модель:** `экономия = N × (время_вручную − время_с_системой)`, ставка 1500 ₽/час
(`DEFAULT_HOURLY_RATE_RUB`).

**Фактический замер владельца** на реальном заказе с FL.ru («Разработка AI-агента для
автоматизации», `fl.ru/projects/5523900/`):

| Этап разбора одного заказа | Время |
|---|---|
| Настройка платформы | ~4 мин (в экономию **не** входит — система его не убирает) |
| Найти, прочитать и понять заказ | 1 мин |
| Оценить свои возможности, затраты времени и цену (когда её нет в заказе) | 5–10 мин, в среднем 7 мин |
| **Итого разбор без настройки** | **≈ 8 мин в среднем** |

Оговорки владельца: это субъективные данные, а не секундомер; у зашедшего впервые время вырастает
более чем вдвое; у заходящего несколько раз в день — существенно меньше.

| Сценарий на 100 заказов | Вручную | С системой | Экономия | В деньгах (1500 ₽/час) |
|---|---|---|---|---|
| Опытный, средний случай (8 мин) | 13,3 ч | 5,0 ч **[оценка 3 мин/заказ]** | **8,3 ч** | ≈ 12 500 ₽ |
| Опытный, худший случай (11 мин) | 18,3 ч | 5,0 ч | **13,3 ч** | ≈ 20 000 ₽ |
| Первый заход на платформу (10 мин) | 16,7 ч | 5,0 ч | **11,7 ч** | ≈ 17 500 ₽ |

**Как считается столбец «в деньгах»:** `(минут_вручную − 3) × 100 / 60 × 1500 ₽`. Ставка
1500 ₽/час — настраиваемый параметр «сколько стоит час вашего времени»
(`DEFAULT_HOURLY_RATE_RUB` в `metrics_service.py`), а не цена заказа; переопределяется на экране
«Метрики и экономика» без правки кода.

Что в этих цифрах измерено, а что оценка:

| Величина | Статус |
|---|---|
| 8 мин вручную, из них 1 мин на поиск и чтение | **замер владельца** на реальном заказе FL.ru |
| 5–10 мин на оценку своих возможностей, времени и цены | **замер владельца** (диапазон), в среднем 7 мин |
| **3 мин с системой** | **оценка из ТЗ §33, владельцем не замерена** |
| 1500 ₽/час | оценочная ставка, настраивается |

Отсюда честный вывод: вся сумма экономии держится на 3 минутах, а это как раз незамеренная величина —
при 2 минутах экономия 15 000 ₽, при 5 минутах 7 500 ₽ на 100 заказов. Замер этого числа —
последняя незакрытая задача в экономике.

Второе уточнение: формула берёт 3 минуты на каждый заказ одинаково, но заказы, отсеянные системой
сами (`skip`), человек вообще не открывает — на демо-прогоне таких 5 из 15. Значит, текущий расчёт
**занижает** экономию. Точная формула считала бы её по классам решений (`apply` / `skip` / `review`).

**Фактические расходы на LLM** (живой прогон, `gpt-4o-mini` через proxyapi.ru, 3 заказа):
3 вызова модели, среднее время ответа 8,9 с, максимум 20,2 с, ошибок 0, все ответы — валидный JSON.

**Расход на модель измерен** отдельным замером на том же заказе FL.ru (промпт `v1.0`,
`gpt-4o-mini`): 1052 токена промпта + 114 токенов ответа = 1166 токенов, промпт 3540 символов.
По тарифу `gpt-4o-mini` это **≈ $0,00023 за анализ**, то есть порядка 2 копеек; на 100 заказов —
меньше 5 рублей против 12 500–20 000 ₽ сэкономленного времени. Расход на модель в этой задаче
незначим.

Оговорка: число получено замером снаружи, а не из системы — проект расход токенов не сохраняет.
Чтобы стоимость считалась по каждому анализу, в аудит достаточно добавить `prompt_tokens`
и `completion_tokens` из ответа модели (провайдер их возвращает) и умножать на тариф.
**[ВАШЕ: при желании сверить с расходом за 6 октября в кабинете proxyapi — там будет наценка шлюза]**

**Честность метрик:** метрики, которые нельзя посчитать (например, доля корректных JSON при нуле
анализов), возвращают **«нет данных»**, а не ноль. Иначе цель «ноль ошибок» выглядела бы достигнутой
на пустой базе.

**Главная экономия — не в скорости анализа, а в отсеве.** На живом прогоне из 3 заказов 1 оказался
чужим (`skip`) — фрилансер не потратил на него ни минуты.

**Реальный заказ с FL.ru, прогнанный через систему** (`fl.ru/projects/5523900/`, `gpt-4o-mini`):
в заказе нет бюджета («пишите свои предложения по стоимости») — система вернула `match_score=null`,
рекомендацию `review` и причину «не указан бюджет» за 12,0 с, не выдумав ни одной цифры.
Тот же заказ с добавленным бюджетом 150 000 ₽ снова ушёл на проверку, но по другой причине:
модель дала 0.90, независимый расчёт по профилю — 0.33, расхождение больше допуска.
Вывод: доля ручной проверки на реальных заказах зависит от полноты профиля — это первое, что нужно
настроить при внедрении. Подробности — `docs/ECONOMICS.md`, разделы 5 и 6.

## 12. Три строки для портфолио (проблема / решение / результат)

1. **Проблема:** фрилансер тратит до 13 минут на разбор одного заказа в ленте, при этом большая часть
   заказов — не его, а часть — с неполными данными.
2. **Решение:** сервис на FastAPI + SQLite с ИИ-анализом заказа, жёсткой схемой ответа и шестью
   бизнес-правилами, которые отправляют спорные случаи человеку с причиной, а заведомо чужие —
   отсекают автоматически; всё под журналом аудита, панель на Streamlit.
3. **Результат:** вердикт по заказу за секунды на реальной модели (от 1,9 до 20,2 с на вызов,
   3 живых прогона прошли без ошибок и без единого невалидного ответа), 7 из 15 разнотипных сценариев
   закрываются без участия человека, спорные уходят в очередь с причиной, каждое решение восстановимо
   по аудиту; 121 автотест, покрытие 96 %, запуск одной командой в Docker.

## 15. Сложности и как решал(а)

**1. Модель врёт там, где не хватает данных.** Первая версия подставляла 0 вместо отсутствующего
бюджета, и заказ с неясным бюджетом выглядел как «нулевая выгода» — то есть решение принималось по
выдуманному числу. Решил так: отсутствие данных — это `null` и явная причина для человека, а не
значение по умолчанию. Потом то же правило пришлось распространить на метрики: «нет данных» вместо
нуля, иначе цель «ноль ошибок» выглядела бы достигнутой на пустой базе.

**2. Доверять самооценке модели нельзя.** Модель выдавала уверенные «подходит», которые при сверке
с профилем не подтверждались. Добавил независимый детерминированный matching engine и правило сверки
оценок: расхождение больше 0.5 → ручная проверка. На живом прогоне это видно: заказ №1 модель оценила
в 1.0, расчёт по профилю дал 0.78 — расхождение в пределах допуска, результат принят; при большем
разбросе заказ ушёл бы человеку.

**3. Порядок бизнес-правил оказался важнее самих правил.** Правило сверки оценок стояло раньше правила
низкой уверенности и перехватывало его: заказ, который должен уйти на проверку с причиной «низкая
уверенность», уходил с причиной «расхождение». Правила пришлось упорядочить по смыслу — сначала
«данных не хватает», потом «уверенность низкая», потом сверка. Обнаружил это тестом на конкретный
случай, а не на общее поведение.

**4. Очередь ручной проверки забивалась мусором.** Правило «сомневаешься — отдай человеку» отправляло
в очередь и заведомо чужие заказы. Пришлось добавить правило уверенного отказа: если и модель, и
расчёт по профилю дают низкое соответствие — система отказывается сама, человека не дёргает.

**5. Аудит терялся именно тогда, когда был нужнее всего.** При ошибке (`HTTPException`) транзакция
откатывалась вместе с записью о неудачном запуске — то есть в журнале не оставалось следа сбоя, хотя
требование ровно обратное. Исправлено явной фиксацией записи аудита перед откатом.

**6. Находки, которые видно только на живом прогоне.** На `mock` всё было зелёным, а с реальной
моделью карточка заказа отдавала `latest_analysis=null`, хотя в списке анализ был: в обработчике
карточки последний анализ просто не запрашивался. Плюс живые вызовы показали то, чего не показывал
mock: время ответа от 1,9 до 20,2 с (при `LLM_TIMEOUT_S=60` запас есть, но холодный DNS съедал время,
поставил 90) и то, что модель честно возвращает `null` для отсутствующего бюджета. Дефект закрыт
фиксом и четырьмя тестами, которые падают на старом коде.

**7. Мелочи окружения, которые съедают часы.** `localhost` на Windows разрешается сначала в IPv6, и
порт 8000 там занимал ретранслятор Docker от чужого контейнера — приложение отвечало `{"detail":"Not
Found"}` при живом сервере. Все адреса переведены на `127.0.0.1`. Ещё: в `.env` пробел после `=`
делал строку невалидной, а `BACKEND_URL=localhost` перекрывал исправленное умолчание в коде.

## 16. План развития

**Ближайшие шаги (после защиты):**

1. **Реальные источники заказов** — FL.ru, Kwork, Freelance.ru, Telegram, RSS как новые классы
   `OrderSource`; бизнес-логика не меняется, потому что источник уже вынесен в отдельный адаптер.
2. **Автосбор** — планировщик → нормализация → дедупликация по паре `(source, external_id)`.
3. **Закрыть последний замер экономики** — время владельца на разбор заказа уже измерено (≈ 8 мин
   без настройки, см. п. 10), осталось засечь время на проверку одной карточки с системой
   (сейчас оценка 3 мин) на 10 заказах.
4. **Профиль и портфолио (RAG)** — подбор реальных проектов из портфолио при генерации отклика.
5. **Уведомления** — Telegram-действие через интерфейс `ActionExecutor`.
6. **Точность** — накопить статистику по решениям человека и настроить порог `match_score` под неё:
   доля `review`, доля принятых решений, доля ложных `apply`.
7. **Автоматические действия** — отправка отклика только после того, как human-in-the-loop доказал
   надёжность на статистике, а не на ощущениях.
8. **Агентная оболочка** — OpenClaw/Hermes как клиент этого API: контракт, аудит и метрики уже есть,
   агенту не хватает ровно их.

**Технический долг:** Alembic вместо `create_all()`, PostgreSQL вместо SQLite, Celery/Redis для
фоновых задач, авторизация в панели. Всё это меняет инфраструктурный слой, не домен.
