# Краткое резюме  
Проект предполагает автоматизацию поиска новых заказов на фриланс-площадках, генерацию и отправку ответов (откликов) с последующей записью данных и уведомлением пользователя. Ключевые задачи: **поиск** вакансий по заданным фильтрам (периодически или по триггеру), **генерация** персонализированного ответа (на основе шаблона и/или LLM с учётом контекста), **отправка** ответа через API или веб-интерфейс площадки, **запись** информации в базу данных и **уведомление** владельца (email, Telegram, webhooks). Рассмотрены варианты архитектуры (монолит, микросервисы, serverless) и использования разных агентов: простой скриптовый агент, LLM-агент (OpenAI), функциональные агенты с вызовом инструментов (OpenAI Function Calling) и фреймворк *Hermes* (многоагентная система). Оценены плюсы/минусы каждого подхода: управление, стоимость API-запросов, задержки, масштабируемость и безопасность. Предложено минимальное MVP (например, поддержка одной-двух площадок, простая архитектура с  сервисами поиска/отправки/оповещений) и примерный план разработки. Приведены таблицы сравнения площадок и агентов, схема БД, диаграмма архитектуры, а также рекомендации по технологиям и методам.

## Обзор фриланс-площадок  
Рассматриваются популярные международные (Upwork, Freelancer.com, Fiverr) и российские (Kwork, FL.ru) площадки (а также *PeoplePerHour*, *Guru* и др.).  
- **Upwork** – глобальная площадка. Предоставляет **официальный API** (GraphQL, OAuth2). Позволяет искать вакансии через endpoints (библиотека запросов существует). Например, поиск объявлений по ключевому слову возвращает JSON-объекты с полями `title`, `description`, `posted_at`, `skills`, диапазоном цены и т.д. (см. пример ответа). Ограничения: требуется регистрация приложения и авторизация; есть rate-limit запросов; некоторые данные (например, детали клиента) могут быть недоступны без контракта. Если API не подходит, можно использовать парсинг: Upwork рендерит страницы через браузер, но публичные результаты можно спарсить (как демонстрирует сторонний парсер).  
- **Freelancer.com** – международная биржа. Имеет **REST API** (OAuth2). Через API можно получать списки проектов, детали, работать с предложениями. Например, официальный «Freelancer API» позволяет получить поля `title`, `description`, `tags/skills`, `bids`, ценовые диапазоны (частичный перечень в RapidAPI). Требуется ключ API. В противном случае можно собирать данные через HTML-скрапинг (Freelancer.com активно защищается от ботов).  
- **Fiverr** – международная биржа услуг (гигов). **Публичного API нет** (и данные на сайте доступны только в интерфейсе). Из-за этого приходится либо использовать сторонние неофициальные API (скрейпинг через Puppeteer или Selenium) либо обходиться без интеграции. Отсутствие открытой документации подтверждает API-трекер (нет упоминаний официальных endpoints). Ограничения: сайт агрессивно защищён от скрапинга (антибот-защита, часто капчи). Возможен парсинг страниц объявлений, но с риском блокировок.  
- **Kwork** – российская биржа быстрых заданий. Официального API нет. Требуется сканировать RSS-фиды (если есть) или парсить HTML. Kwork относительно прост в скрапинге (иногда доступно RSS или JSON через API из браузера).  
- **FL.ru** – российская биржа («Free-lance.ru»). Тоже не предоставляет API для разработчиков. Данные (вакансии) можно получить только путём HTML-парсинга или обхода их внутренних API при открытии сайта (опасно с точки зрения ToS).  
- *Другие площадки:* *PeoplePerHour*, *Guru*, *Habr Freelance*, *Work-zilla* и др. У многих нет открытых API (необходимо скрапить) или они узко ориентированы (Work-zilla для мелких задач).  
В таблице ниже сравнение по API и методам доступа (для примера):

| Площадка        | API-доступ                     | Ограничения / способ парсинга            |
|-----------------|--------------------------------|-----------------------------------------|
| Upwork          | Есть GraphQL API (OAuth2)      | Нужно зарегистрировать ключ, есть лимиты; без API можно скрапить рабочие страницы |
| Freelancer.com  | Есть REST API (OAuth2)         | Необходима регистрация приложения; без API – скрапинг JSON/HTML интерфейса |
| Fiverr          | Нет публичного API            | Используют веб-страницы, нет официального доступа (как отмечено на API-трекере) |
| Kwork           | Нет API (неофициально – RSS)  | Доступ через RSS/HTML; простые страницы, но «автоматизация» может противоречить правилам |
| FL.ru           | Нет API                         | HTML-парсинг; возможны анти-скрапинг меры |
| *Прочие (PPH, Guru)* | Обычно нет API или узкий доступ | Скрейпинг (Risk), RSS если есть |

Для платформ с API предпочтительно использовать **официальные SDK или прямые HTTP-запросы**. При отсутствии API – использовать легальный парсинг (учитывая `robots.txt`, частоту запросов и вероятность блокировок). Всегда необходимо уважать *Terms of Service* площадки и избегать превышения лимитов.

## Архитектура системы  
Возможны следующие подходы: **монолит** (всё как единое приложение), **микросервисы** (разделение на сервисы по функциям), **serverless** (функции в облаке, событийная обработка), **edge** (выполнение ближе к пользователю для снижения задержки, не критично тут). 

На практике целесообразна гибридная архитектура с микросервисами и очередями. Компоненты: 

- **Сервис поиска заказов (JobFetcher)** – периодически (cron) или по вебхуку опрашивает площадки (API или парсинг) с нужными фильтрами. Полученные вакансии отправляет дальше через очередь сообщений.  
- **Очередь сообщений (RabbitMQ, Kafka, AWS SQS и т.п.)** – буфер между сервисами, гарантирует надёжность, позволяет организовывать ретраи при сбоях.  
- **Сервис генерации ответа (ResponseAgent)** – получает задания из очереди, извлекает всю информацию о заказе и клиенте, при необходимости дополняет из портфолио/истории и формирует ответ. Это может быть простая шаблонная логика или обращение к LLM (ChatGPT/модель).  
- **Сервис отправки отклика (Sender)** – принимает сгенерированный текст и отправляет ответ заказчику: через API площадки (если есть endpoint для оффера/заявки) или эмулируя действия в веб-интерфейсе (авторизованный сеанс, заполнение формы).  
- **База данных (Postgres, MongoDB или Redis)** – хранит историю найденных вакансий, ответов и их статусы. Помогает не отвечать дважды на одну задачу, анализировать конверсию.  
- **Модуль уведомлений** – по успешной/неуспешной отправке или при событиях (новые подходящие заказы) оповещает пользователя по email, через Telegram-бота или webhooks в другие системы.  

Возможна **монолитная версия MVP**, где все функции выполняются одним приложением. Однако для надёжности/масштабирования лучше микросервисный подход: каждый шаг (парсинг, генерация, отправка) развернут отдельно, легко масштабируется, может выполняться в serverless (например, AWS Lambda на события). Хранение «состояний агентов» (например, контекст сессии LLM или кеш) можно реализовать через Redis/ин-мемори или таблицы БД. Диаграмма архитектуры с потоками показана ниже:


*Комментарии к диаграмме:* Сервис **JobFetcher** выполняет поиск объявлений (получает уведомления платформы или опрашивает API) и публикует задачи в **очередь**. **ResponseAgent** (агент) обрабатывает каждую задачу, формирует ответ (с помощью моделей GPT или правил), сохраняет результат в **БД** и передаёт **Sender** для отправки. После отправки создаётся запись в БД и высылается уведомление владельцу. Между сервисами применяется аутентификация и контролируются повторные попытки (retry) на случай неудачных запросов. 

## Варианты агентов автоматизации  
Сравниваются четыре подхода:

| Подход            | Механизм                                         | Контроль и безопасность                         | Задержки и стоимость                          |
|-------------------|--------------------------------------------------|-------------------------------------------------|-----------------------------------------------|
| **Rule-based агент**  | Детерминированные скрипты/шаблоны. Проверки на совпадение ключевых слов, автоформирование ответа по шаблону с подстановкой данных. | Полный контроль (статический код). Низкий риск «непредсказуемых» действий. Легко логировать. | Высокая скорость (нет внешних вызовов). Низкие издержки, но ограниченные возможности по качеству ответов. |
| **LLM-агент (OpenAI)** | Использует GPT-модель (ChatGPT API) для генерации ответа по контексту (описание заказа, портфолио и др.). | Можно задать «системное сообщение» с правилами. Но модель генерирует непрозрачно (контроль только через входные подсказки). Степень предсказуемости ниже. Вопросы безопасности: утечка данных (контекст передаётся в OpenAI), контроль задержек. | Высокие задержки (запрос → ответ модели, ~ сотни мс). Стоимость – оплата токенов (зависит от длины запросов/ответов). |
| **OpenAI Agents / Tool-агент** | GPT с *Function Calling* или в рамках Agent Framework. Модель сама вызывает «инструменты» (API площадок) и может выполнять пошаговые задачи (поиск, анализ, отправка). | Более высокая степень автоматизации (модель сама планирует действия). Но сложнее контролировать (модель может «ошибочно» вызвать что-то). Tool-сессии логируются, можно задать ограничения. Риск: цепочка запросов. | Нагрузочные задержки могут возрасти (несколько подряд вызовов API/OpenAI). Стоимость – суммарно за все вызовы модели и API. |
| **Hermes Agent (Nous Research)** | Открытый фреймворк для мультиагентной системы. Поддерживает несколько LLM, память, интеграции (Telegram, API, webhook и т.д.). Агент можно «обучать» сохранением навыков. | Высокий контроль: поддерживает профили, изолированные сессии, пулы ключей, плагины. Имеет встроенные механизмы безоп. Можно запускать локально или в облаке. | Задержка зависит от выбранной модели и среды (локальная модель – быстро, облачная – медленнее). Hermes сам по себе бесплатен, но в нём используются LLM, так что стоимость запросов зависит от API. |

Hermes – это фреймворк, который «из коробки» поддерживает вызов инструментов, хранит персистентную память и умеет интегрироваться в чат-приложения. Он может быть развернут локально или на сервере под вашим контролем (в отличие от ChatGPT, который – облачный сервис OpenAI). OpenAI Agents (новый SDK) позволяют использовать GPT-4 для планирования действий, но это экспериментальное решение от OpenAI. Rule-based скрипты – самый простой и надёжный вариант (низкий latency и прямой контроль), но требует разработки шаблонов под каждый тип задач. 

**Инструменты/плагины для API:** и OpenAI, и Hermes поддерживают «инструменты» (tool plugins) – программируемые API-функции. Например, в OpenAI Function Calling можно описать JSON-схему функции для запроса к API площадки (поиск вакансий, отправка предложения). Hermes использует концепцию «skills» и MCP-серверов, позволяющих вызвать любую функцию через HTTP/CLI. Таким образом, можно реализовать calls к API Upwork/Freelancer как «инструменты», которые агент дергает по необходимости.

## Схема базы данных  
Для хранения данных целесообразен реляционный Postgres (структурированные вакансии и отклики) с возможностью JSON-полей, либо MongoDB (гибкая схема) + Redis (для кэша/сессий). Ниже приведён пример таблиц и колонок:

| Таблица          | Поле             | Тип            | Описание                                   |
|------------------|------------------|----------------|--------------------------------------------|
| **Jobs**         | `id`             | BIGINT (PK)    | Внутренний ID задания                      |
|                  | `platform`       | VARCHAR        | Название площадки (Upwork, Freelancer и т.д.) |
|                  | `external_id`    | VARCHAR        | ID вакансии на площадке                    |
|                  | `title`          | TEXT           | Заголовок задания                         |
|                  | `description`    | TEXT           | Описание задания                          |
|                  | `skills`         | TEXT[]/JSON    | Список требуемых навыков                  |
|                  | `budget_min`     | NUMERIC        | Минимальный бюджет (или ставка)           |
|                  | `budget_max`     | NUMERIC        | Максимальный бюджет (или ставка)          |
|                  | `budget_type`    | VARCHAR        | Тип бюджета (hourly/fixed)                |
|                  | `posted_at`      | TIMESTAMP      | Дата публикации                           |
|                  | `crawled_at`     | TIMESTAMP      | Дата и время первого обнаружения          |
|                  | `status`         | VARCHAR        | Статус (new/responded/archived)           |
| **Responses**    | `id`             | BIGINT (PK)    | Внутренний ID отклика                     |
|                  | `job_id`         | BIGINT (FK)    | Ссылка на задачу                           |
|                  | `message`        | TEXT           | Текст отправленного ответа                |
|                  | `sent_at`        | TIMESTAMP      | Время отправки                            |
|                  | `result`         | VARCHAR        | Результат (accepted/rejected/error)       |
| **Notifications**| `id`             | BIGINT (PK)    | ID оповещения                             |
|                  | `job_id`         | BIGINT (FK)    | Ссылка на задачу                           |
|                  | `channel`        | VARCHAR        | Канал (email, telegram, webhook)          |
|                  | `sent_at`        | TIMESTAMP      | Время отправки уведомления                |
|                  | `status`         | VARCHAR        | Статус (sent/failed)                      |

Такое разделение позволяет хранить вакансию один раз и отслеживать все отправленные по ней ответы, уведомления и статусы. Redis можно использовать для кэширования состояний агентов (например, промежуточная память диалогов) и очередей задач (если нужен быстрый in-memory буфер).

## Безопасность и риски  
- **Rate limits и анти-бот:** Большинство API имеют ограничения по числу запросов в минуту. Например, Upwork и Freelancer вводят собственные лимиты. При парсинге необходимо учитывать `robots.txt` (хотя это рекомендация, а не закон) и лимитировать частоту, чтобы не привести к блокировке IP или аккаунта. Анти-бот-системы (Cloudflare, reCAPTCHA и т.д.) могут препятствовать скрапингу, поэтому для парсинга целесообразно использовать headless-браузер с прокси и случайными задержками.  
- **Соблюдение правил (TOS):** Автоматическая подача заявок может нарушать правила площадки. Многие платформы запрещают «массовые» или «автоматические» заявки без ручного контроля. Нужно внимательно изучить *Terms of Service* каждой площадки. Например, если платформа разрешает использовать API – действия по API обычно безопасны, а вот «кликать» по веб-интерфейсу автоматически – сомнительно.  
- **GDPR и РФ-законодательство:** Если система обрабатывает персональные данные (например, контактные данные заказчиков или фрилансеров), необходимо обеспечить защиту этих данных и соответствие GDPR/152-ФЗ (хранение в РФ, шифрование, согласие). Рекомендуется шифровать токены доступа (OAuth токены) и PII в БД. Например, практики по хранению OAuth рекомендуют **шифровать refresh-токены** и держать ключи в менеджере секретов.  
- **Аутентификация и хранение токенов:** Токены доступа к API (OAuth) следует хранить в зашифрованном виде или в безопасном хранилище (Vault). При возможности использовать короткоживущие токены и обновлять их (rotate). Логи аудита нужны для отслеживания действий агентов и запросов к площадкам.  
- **Юридические риски:** Возможны претензии со стороны площадок (блокировка аккаунта, аннулирование откликов) в случае, если система нарушает их правила. Также автоматизация может привести к нежелательному рассыланию однотипных заявок, что рассматривалось бы как «спам». На уровне организации стоит предусмотреть согласие пользователя на такие действия и логи с записями каждого действия.  
- **Ошибочные заявки (False Positives):** Агент может ошибочно определить неподходящий заказ или некорректно сформулировать ответ, что приведёт к потере репутации или даже жалобам. Необходима тщательная проверка шаблонов и мониторинг результатов (KPI, см. ниже).  

## План MVP (минимально жизнеспособный продукт)  
**Технологический стек:** для прототипа подойдёт Python (requests/HTTP для API, BeautifulSoup/Selenium для парсинга), фреймворки агентов (например, использование [LangChain](https://langchain.com) или OpenAI SDK для LLM), база Postgres или MongoDB, RabbitMQ или Celery для очередей. Уведомления – через Telegram Bot API или SMTP/email (есть готовые библиотеки). Для LLM – OpenAI API (GPT-4/GPT-3.5).  

**Функциональный минимум:** реализовать интеграцию с одной площадкой (скажем, Upwork или Freelancer) по API. Автоматически искать вакансии (по ключевым словам), фильтровать по критериям. Генерировать ответ: первый этап – статический шаблон с подстановкой (название вакансии, имя владельца, краткая информация из портфолио). Второй этап (дополнительно) – подключить GPT для персонализации. Отправлять ответ через API (если доступно) или эмулировать веб-запрос (использовать Selenium). Записывать данные в базу. Уведомлять пользователя о новом ответе (например, в Telegram).  

**Roadmap:**  
1. **Исследование и подготовка:** изучить документацию API выбранной площадки, получить API-ключи, сформулировать фильтры поиска.  
2. **Парсинг/Поиск:** написать скрипт для поиска вакансий и записи их в БД.  
3. **Генерация ответа:** создать шаблон и интегрировать LLM (через OpenAI API). Тестировать на нескольких примерах.  
4. **Отправка:** реализовать отправку через API площадки (или эмуляцию).  
5. **Уведомления:** добавить отправку уведомлений (Telegram или email).  
6. **Логирование и метрики:** подключить сбор логов, простое отслеживание KPI (см. ниже).  
7. **Тестирование:** провести нагрузочное тестирование с частотой запросов, откалибровать расписание.  
8. **Деплой:** развернуть в облаке (например, Heroku/AWS/Docker).  

**Оценка ресурсов:** прототип может быть сделан небольшой командой (1–2 разработчика) в сроки ~1–3 месяцев. Задачи – backend, интеграция LLM, DevOps для CI/CD. Бюджет: от зарплат разработчиков плюс затраты на облако (сервер) и API (OpenAI). Точных цифр нет, но сам код может быть минимальным (несколько тысяч строк). Ориентировочно, при аутсорсе – десятки тысяч долларов, при штатной команде – аналогичный эквивалент в чел.-днях. Основные расходы – оплатить LLM (OpenAI: ~$0.03 за 1K токенов для GPT-4) и хостинг.  

## Тестирование и метрики  
Ключевые метрики (KPI) для оценки эффективности:  
- **Количество найденных заказов** (в день) – проверка полноты поиска.  
- **Скорость реакции (Response rate)** – доля новых заказов, на которые был отправлен ответ.  
- **Конверсия (Conversion rate)** – доля принятых ответов (клиент откликнулся или заказ оформлен). Помогает оценить качество ответов.  
- **Ложные срабатывания (False Positives)** – число ответов по неподходящим вакансиям (или где клиент не проявил интерес).  
- **Время обработки** – средняя задержка от момента появления заказа до отправки отклика. Должна быть минимальной (чтобы не опоздать).  
- **Надёжность (uptime)** – процент успешных вызовов API и доставленных уведомлений.  

Для мониторинга: логирование всех шагов (например, с помощью ELK-stack или Grafana), трекинг ошибок/исключений. Настроить алерты на падения отправки заявок. Можно использовать встроенные инструменты cloud-провайдера. При аутсорсе мониторинга – Sentry для ошибок, Prometheus/Grafana для метрик.  

## Рекомендации по стеку и технологиям  
- **Язык:** Python – богат экосистемой для HTTP (requests, aiohttp), парсинга (BeautifulSoup, Selenium), работы с очередями (Celery, aiojobs) и LLM (OpenAI-пакет, LangChain, библиотеки для HuggingFace).  
- **LLM-интеграция:** использовать официальный OpenAI Python SDK с функцией *function calling*. Это позволит GPT сам формулировать нужные вызовы (например, получать данные о заказе или отправлять отклик). Для более свободного прототипа можно начать с простого `chat_completion`.  
- **API-подключения:** предпочтительны официальные библиотеки площадок. Например, для Upwork есть open source библиотеки-клиенты. Если их нет – обёртки над HTTP. Для Telegram-уведомлений – `python-telegram-bot` или `aiogram`. Для email – SMTP библиотеки или сервис (Mailgun, SendGrid).  
- **База данных:** Postgres – надёжно, поддерживает сложные запросы и JSON-поля. MongoDB – гибкий JSON-подход для разных схем вакансий. Redis – для кеша результатов поиска и хранения коротких сессий агентов.  
- **Очереди и задачи:** RabbitMQ, Kafka или облачные SQS для связки сервисов. Celery (Python) с Redis/RabbitMQ – готовый инструмент для фоновых задач (поиск, обработка, отправка).  
- **Архитектура:** рекомендуем микросервисы и контейнеризацию (Docker, Kubernetes или Fargate). Serverless-функции (AWS Lambda/Azure Functions) можно использовать для webhook-обработчиков или крауд-парсинга (но сложнее отлаживать).  
- **Безопасность:** хранить конфиги и токены в переменных окружения или секретных хранилищах (AWS Secrets Manager). Шифровать чувствительные данные в БД. Логировать операции для аудита и отладки.  

**Источники и дополнения:** Для детальной интеграции использовать официальную документацию API площадок, инструкции OpenAI (раздел *Function Calling*) и документацию Hermes (описывает, как создавать и расширять агента). Русскоязычные материалы по фрилансу полезны для понимания специфики: блоги на Habr, статьи про биржи (например, обзоры Upwork vs Kwork и др.).
