# Журнал проекта AI Freelance Copilot (MVP)

Пишется по ходу работы — история решений, а не пересказ ТЗ.

## 2026-10-06 — MVP собран и проверен

**Сделано.** Полный каркас по ТЗ: модульный монолит (FastAPI + домен + инфраструктура +
Streamlit), 4 доменные таблицы + аудит, три точки доступа, строгая схема результата,
6 бизнес-правил ручной проверки, matching engine, аудит, метрики и мини-экономика,
Docker-обвязка, 117 тестов (покрытие app/ 96%), набор тестовых данных, документация.

**Проверено вживую.** Backend поднят на `127.0.0.1:8000`, `scripts/seed_demo.py` создал 4 заказа
и прогнал 4 анализа, панель Streamlit открыта в браузере: экраны «Обзор», «Заказы»,
«Карточка заказа», «Требуют проверки», «Аудит и ошибки» работают; ручное решение по заказу #3
принято через панель и попало в аудит (`review_decision`, статус `approved`).

**Решения, принятые по ходу:**

1. **Провайдер OpenAI-совместимый, а не «OpenAI».**, `api.openai.com`
   недоступен. Один адаптер с параметром `LLM_BASE_URL` закрывает OpenAI, proxyapi.ru, DeepSeek
   и локальную ollama, поэтому переключение модели — правка `.env`, а не кода.
2. **Детерминированный matching engine добавлен сверх ТЗ.** Без него правило §14.3
   («соответствие определить не удалось») нечем проверить: мнение модели не с чем сверить.
   Заодно появился воспроизводимый `match_score`, покрытый юнит-тестами.
3. **Правило 5 получило исключение.** Иначе неподходящие заказы (например, вёрстка лендинга для
   Python-профиля) валились бы в очередь ручной проверки и превращали её в мусорную свалку.
   Условие: и модель, и расчёт по профилю дают низкое соответствие, модель говорит `skip`.
4. **Аудит не теряется при ошибке.** Сессия БД фиксируется при `HTTPException`, а не
   откатывается: иначе запись о неудачном запуске (404, ошибка валидации) исчезала бы, а ТЗ §29.4
   требует обратного. Откат остался для настоящих внутренних сбоев.
5. **Метрика на пустом входе = `null`, а не `0`.** Цель «ноль ошибок» на пустой базе
   выглядела бы достигнутой. Проценты при нулевом знаменателе не считаются, в UI — «нет данных».

**Найденные и исправленные дефекты (все до сдачи):**

| Дефект | Как проявлялся | Исправление |
|---|---|---|
| `Protocol OrderSource` перекрывал доменный `OrderSource` | источник по умолчанию молча терялся | импорт под псевдонимом `OrderSourceKind` |
| in-memory SQLite в тестах давала «no such table» | integration-тесты падали на первом запросе | `StaticPool` для in-memory URL |
| Очередность правил: низкая уверенность перехватывалась сверкой score | правило «ниже порога» никогда не срабатывало | правило 5 поднято выше правила 6 |
| `frontend/app.py` импортировал несуществующий символ из `ui` | панель падала в `ImportError` | импорт исправлен, панель проверена в браузере |
| Лишняя строка-заглушка в репозитории заказов | не влияла, но мусор | удалена |
| Единый Dockerfile для обоих сервисов | frontend наследовал healthcheck backend и вечно висел `unhealthy` | разделены `Dockerfile.backend` / `Dockerfile.frontend`, у backend healthcheck и `depends_on: service_healthy` |
| Жёсткие порты 8000/8501 в compose | конфликт с чужим контейнером на 8000 (`faceid-core-api`) | порты вынесены в `BACKEND_PORT` / `FRONTEND_PORT` |

**Дефект окружения, найденный при живом прогоне.** `curl http://localhost:8000/api/v1/health`
возвращал `{"detail":"Not Found"}`, хотя сервер работал. Причина не в приложении: на Windows
`localhost` разрешается сначала в IPv6, и `[::1]:8000` держал `wslrelay.exe` (ретранслятор
Docker от чужого контейнера на 8000), который и отвечал 404. На `127.0.0.1:8000` отвечает
наш uvicorn. Исправлено во всех умолчаниях и документации: `127.0.0.1` вместо `localhost`
(`api_client.py`, `config.py`, `seed_demo.py`, `.env.example`, README, docs/API.md, docs/DOCKER.md).

**Проверка Docker (2026-10-06).** Демон Docker Desktop на машине поднимается только
ручным запуском (`"C:\Program Files\Docker\Docker\Docker Desktop.exe"`) — из фонового шелла
он стартует и через минуту-две отваливается. После запуска вручную:

```text
BACKEND_PORT=8300 FRONTEND_PORT=8601 docker compose up --build -d
copilot-backend    Up (healthy)   0.0.0.0:8300->8000/tcp
copilot-frontend   Up             0.0.0.0:8601->8501/tcp
POST /api/v1/orders → 201, POST /api/v1/orders/1/analyze → success, match_score 1.0
панель на 8601 отдаёт данные из контейнерного backend
```

## 2026-10-06. Живой прогон на реальной модели (proxyapi, `gpt-4o-mini`)

Первый прогон не на `mock`. Три заказа разных типов, ключ оставался в `.env` (в чат и логи не выводился),
провайдер включался переменной окружения, база — отдельный файл `artifacts/live.db`.

Результат: `apply` (100 % соответствия, черновик отклика) / `review` (нет бюджета, `match_score=null`) /
`skip` (чужой стек, 0 %). Все три ответа — валидный JSON, ошибок LLM ноль, `avg_analyze_duration_ms`
8 935 (от 1 944 до 20 177 мс), решение человека записано в аудит. Экспорт — `artifacts/*-live-*.json/.csv`.

Что живой прогон дал сверх `mock`:

1. **Дефект: карточка заказа теряла последний анализ.** `GET /api/v1/orders/{id}` отдавал
   `latest_analysis: null`, хотя в витрине анализ был: в обработчике карточки последний анализ не
   запрашивался вовсе (`_to_out(order)` без аргумента). Панель спасалась отдельным вызовом
   `client.latest_analysis()`, поэтому дефект не был виден в UI — врал только API. Закрыт фиксом
   (`OrderService.latest_analysis()`) и четырьмя тестами `tests/integration/test_order_detail.py`,
   которые падают на старом коде (проверено временным откатом).
2. **Реальное время ответа модели** — 1,9–20,2 с против 5–20 мс на `mock`. При `LLM_TIMEOUT_S=60`
   запас есть, но холодный DNS съедал время, поэтому таймаут поднят до 90.
3. **Модель честно возвращает `null`** для отсутствующего бюджета и сама пишет причину «не указан
   бюджет» — правило 1 ТЗ §14.1 работает на реальной модели так же, как на mock.
4. **Правило сверки оценок проверено живьём:** модель дала 1.0, независимый расчёт по профилю — 0.78;
   расхождение 0.22 меньше допуска 0.5, поэтому результат принят, а не отправлен человеку.

Дефекты окружения, найденные при подготовке: в `.env` лишний пробел после `=` в `LLM_BASE_URL`
(строка невалидна) и `BACKEND_URL=localhost`, перекрывающий исправленное умолчание `127.0.0.1` в коде.
