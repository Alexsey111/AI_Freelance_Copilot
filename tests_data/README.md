# tests_data — набор тестовых данных

Один и тот же набор читают pytest (`tests/integration/test_tests_data_suite.py` через
`tests/fixtures/tests_data_set.py`) и скрипт сквозного прогона
(`scripts/run_tests_data.py`). Поэтому «тестовые данные» и «тесты» не могут разойтись:
файлы — единственный источник правды.

## Файлы

| Файл | Что внутри |
|---|---|
| `inputs.jsonl` | 15 входных заказов: `id`, `rule` (какое правило ТЗ проверяется) и `payload` — тело запроса к `POST /api/v1/orders` |
| `specs.jsonl` | ожидаемый результат каждого сценария: `needs_review`, `recommendation`, границы `match_score`, наличие черновика, `audit_status`, `order_status`, подстрока в `review_reason`, поле `why` |
| `events.jsonl` | ожидаемое событие аудита (`audit_action`, `audit_status`) на каждый ключевой сценарий |
| `queries.jsonl` | 10 запросов к витрине: параметры, ожидаемый `total`, количество элементов в странице, ожидаемый HTTP-код |

Формат JSONL: одна JSON-запись на строку, кодировка UTF-8, пустые строки и строки,
начинающиеся с `//`, игнорируются.

## Что покрывает набор

15 сценариев — не «10 однотипных заказов», а по одному-два на каждый случай из ТЗ §14:

| Сценарий | Что проверяет | Правило ТЗ |
|---|---|---|
| `S01_telegram_bot` | полное покрытие стека профилем → `apply` + черновик | базовый |
| `S02_parser_excel` | сильная сторона профиля (парсинг, выгрузка) | базовый |
| `S03_tilda_landing` | уверенный отказ: чужой стек, человека не дёргаем | §14 |
| `S04_1c` | уверенный отказ: 1С | §14 |
| `S05_seo` | уверенный отказ: SEO | §14 |
| `S06_mobile_flutter` | уверенный отказ: мобильная разработка | §14 |
| `S07_no_budget_long` | **ручная проверка**: нет бюджета при достаточном описании | §14.1 |
| `S08_vague_short` | **ручная проверка**: нет ни бюджета, ни объёма работ | §14.1 / §13 |
| `S09_partial_match` | **ручная проверка**: уверенность модели ниже порога | §14.3 |
| `S10_php_only` | уверенный отказ: PHP/Laravel | §14 |
| `S11_analytics_borderline` | **ручная проверка**: модель сама просит человека | §14.3 |
| `S12_llm_bad_json` | **ручная проверка**: невалидный JSON модели | §14.2 / §29.3 |
| `S13_llm_timeout` | **ошибка LLM**: заказ в `error`, аудит всё равно записан | §14.5 / §29.4 |
| `S14_llm_no_draft` | **ручная проверка**: `apply` без черновика понижен до `review` | §14.4 |
| `S15_llm_inflated` | **ручная проверка**: оценка модели расходится с расчётом по профилю | §14.6 |

Итого **8 сценариев с `needs_review=true`** (требование сдачи — минимум 1–2), каждый со своей
причиной, а не один случай в восьми копиях.

Сценарии `S09`, `S11`–`S15` включаются служебным префиксом в заголовке заказа
(`MOCK_LOW_MATCH`, `MOCK_LOW_CONFIDENCE`, `MOCK_BAD_JSON`, `MOCK_TIMEOUT`, `MOCK_NO_DRAFT`,
`MOCK_INFLATED`). Префикс понимает только `MockProvider` — так аварийные ветки проверяются
сквозь API и сквозь бизнес-логику, а не только юнит-тестом на внутреннем методе.
На реальной модели такие же сценарии дают те же правила, но триггер, разумеется, другой:
невалидный JSON, timeout и расхождение оценки случаются сами.

## Как запустить

```bash
# через pytest (база и сервер не нужны, поднимается TestClient)
./.venv/Scripts/python.exe -m pytest tests/integration/test_tests_data_suite.py -q

# сквозной прогон по живому API + экспорт артефактов (JSON и CSV)
./.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000   # терминал 1
./.venv/Scripts/python.exe scripts/run_tests_data.py                              # терминал 2
```

Первый вариант удобен для проверки, второй — для демонстрации и отчёта: он печатает таблицу
«сценарий → решение → причина → статус аудита» и складывает результаты в `artifacts/`.
